# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## ezytrip decisions

- User feedback (2026-10-23): prioritize the mobile trip planner as the product's main workflow. Hotel discovery is optional and should stay secondary on the homepage; improve day planning and activity editing before expanding stay search.
- User feedback (2026-10-23): the place/day planning view should make a map visually prominent, inspired by the shared Pinterest map-art board. Keep illustrative maps distinct from verified coordinates or navigation until a permitted real map data source is selected.
- User feedback (2026-10-23): use the Ponpon Mania interactive comic design system as inspiration only (adapt, do not copy). Keep the mobile-first Trip Planner as the primary workflow, with an expressive bento grid, visually prominent illustrative map and daily plan, and stays secondary. Follow `DESIGN.md` for the palette, radii, spacing, and responsive requirements.
- This is a responsive web application primarily used on phones, not a native app or device-frame simulation. Preserve the compact travel-utility homepage, readable Thai labels, bottom navigation and bottom sheets. The earlier desktop marketing/collage concepts were rejected.
- Use MapLibre GL JS with OpenFreeMap's hosted vector tiles for the trip map under the free-first constraint. Keep visible OpenFreeMap/OpenMapTiles/OpenStreetMap attribution. The current trip-stop coordinates and connecting line are demonstration estimates only; do not present them as verified places, routing or navigation. Recheck the provider's free terms and availability before production use.
- Keep motion playful but brief: a selected trip-map pin can pop once, its detail card can enter gently, and confirmation toasts can appear softly. Respect `prefers-reduced-motion`; avoid looping or attention-grabbing movement.
- User feedback (2026-10-24): when adding a destination, let the traveler pin its real map location and choose walking, road or MTR/transit routing; draw only routes returned from a real routing source and show the transit station/line. Keep the free-first prototype attribution visible and respect public routing limits; send MTR itineraries to a real transit planner until the project has a hosted GTFS/OpenTripPlanner route engine. For sample places, a real routed geometry may be shown as a dashed line with an explicit approximate-location label; never draw an estimated straight line as a real route.
- User feedback (2026-10-24): show bus lines and boarding/alighting stop names as chat bubbles on the map. The prototype now reads the Transport Department/KMB public stop, route-stop and route-list APIs; only show direct routes when the ordered stop sequences connect both endpoints, otherwise show nearby route bubbles and clearly say a transfer may be needed. Any road geometry inferred between official stops must be labeled approximate; stop data is cached only in memory for the current day.
- User feedback (2026-10-24): use the shared Figma mobile Trip Planner frame (`e4XCgnL83tw2OlHvpf2fQ4`, node `5:2`) as the layout reference: horizontally selectable day chips, map before itinerary, warm neutral canvas, teal route accents, and a compact grouped itinerary with a friendly helper note. Adapt colors/components to ezytrip and keep the interactive MapLibre map and route trust labels; do not replace them with Figma's schematic map or imply estimated paths are real.
- User feedback (2026-10-24): continue local work without requiring the user to keep the Mac screen open; skip steps requiring user account setup/approval, and do not use paid services or actions.
- User feedback (2026-10-24): make typography feel current and youthful while keeping Thai highly readable on mobile; prefer installed system fonts and clear size/weight hierarchy over decorative type or remote font downloads.
- User feedback (2026-10-24): the daily plan needs a stronger layout redesign, not just pastel recoloring; keep activity times compact, make each stop easy to scan and edit, and allow comparison of playful, colorful, minimal, and mixed treatments during design review.
- User decision (2026-10-24): use Playful as the main daily-plan direction and make it more fun; remove the temporary design comparison controls from the product UI while keeping the mobile schedule readable and editable.
- Free-first is a hard project constraint. Use existing local tools and freely licensed assets; do not trigger paid generation, subscriptions, paid APIs or deploy without explicit authorization and cost verification. Current assets are local Unsplash-license photographs with provenance in `public/assets/sources.json`; use them only as illustrative content for fictional hotels.
- The five routes are `/`, `/search`, `/stays`, `/stay/:id`, `/trip` through hash navigation. Keep the search → list → detail → save → trip journey working.
- `src/domain.js` holds money/date/budget calculations; `src/data.js` holds synthetic content; `src/App.jsx` holds UI and local state; `src/styles.css` holds responsive styles. Prefer extracting screen components as scope grows.
- Recorded amounts use integer HKD cents. Currency swap is presentation only. Search budgets record their input currency so filtering stays stable when the display changes. Never replace the synthetic rate with a claimed live value without a real source and freshness handling.
- Local storage is for demo state only. Invitations, permissions, hotel comparisons, routes and weather are clearly labeled demonstrations or unconnected states. Do not imply real collaboration, server authorization, actual bookings or verified travel advice.
- Use pnpm and `pnpm-lock.yaml`. `pnpm test` runs six domain tests plus four template hosting tests. `pnpm run build` creates the local build; it does not authorize publishing. The preview is bound to `127.0.0.1:4173` only.
